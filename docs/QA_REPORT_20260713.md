## Provider configuration and runtime boundary

The source requests:

- model `gemini-3.1-pro-preview` at `server.py:44`;
- image plus text in one GenerateContent request at `server.py:1241-1261`;
- JSON MIME type and `ANALYSIS_RESPONSE_SCHEMA` at `server.py:1253-1260`;
- `ThinkingLevel.HIGH` at `server.py:1258-1260`;
- `max_output_tokens=65536` at `server.py:1255`;
- `google-genai==2.11.0` at `requirements.txt:5`.

Google's official [Gemini 3.1 Pro Preview model page](https://ai.google.dev/gemini-api/docs/models/gemini-3.1-pro-preview) lists image input, structured outputs, and thinking as supported. Google's official [thinking guide](https://ai.google.dev/gemini-api/docs/thinking) lists low, medium, and high thinking for `gemini-3.1-pro-preview`.

Static configuration is not proof that a network call succeeds. An isolated environment at `work/venv312` was created with Python 3.12.13 and the exact current `requirements.txt`; it installed `google-genai==2.11.0`, instantiated the exact structured-output and `ThinkingLevel.HIGH` configuration, and passed all 33 Python tests. The older project `venv` remains Python 3.9.6 with `google-genai` 1.47.0 and must not be used as release evidence. A real preview HIGH call still requires a rotated preview-only credential or isolated preview deployment.

The macOS and Windows startup helpers now direct users to `GOOGLE_API_KEY`, verify `google-genai==2.11.0` and `ThinkingLevel.HIGH`, and stop if dependency installation fails. Startup output reports only whether a key is configured; it does not echo any portion of the credential. The stale Claude fallback and mixed-provider timeout comments were also corrected. A regression test scans the runtime-facing page, server, dependency, launcher, and Gunicorn surfaces and requires them to remain Google-only.

`DEPLOY-GUIDE.docx` and `SETUP-GUIDE.docx` now describe the Google AI Studio key flow and `GOOGLE_API_KEY`; neither retains an Anthropic key instruction. Both archives passed structural checks and were rendered page by page for visual inspection. These are provider substitutions within the existing guide layouts, not a documentation redesign.

## Clinical and recommendation validation boundary

No evidence in this QA run supports any of these claims:

- clinically validated skin analysis;
- diagnostic accuracy or reliable detection of concerning lesions;
- accurate or calibrated concern scores;
- accurate mapping from appearance to Von & Co services or products;
- quality equal to or better than Haut.ai;
- complete or current studio service and product catalogs.

The concerning-lesion sentence is only a fixed small-print referral instruction. At Brandon's direction, the model prompt explicitly does not ask Gemini to identify, assess, flag, rule out, or comment on lesions or medical conditions. The app must not be presented as capable of identifying or ruling out a lesion that needs medical evaluation.

Before release, a clinician-labeled set must include multiple independent face, neck and chest, hands, back, and legs photos across varied skin tones, lighting, framing, resolution, and devices. Each case needs documented expected intake outcome, visible priorities, acceptable service and product options, and options that should not appear. A clinician must review the generated outputs against those labels.

Separately, the studio must sign off on the exact current service catalog, product catalog, offer language, Club price, Club benefits, booking URLs, phone number, hours, timing language, image-storage privacy language, and any experience or VISIA claims. The presence of those values in source code is not evidence that they are current.

## Known preserved limitation

Guided Capture collects front, left, and right views but submits only `guidedPhotos[0]`. The server receives one `image` field. This is not multi-image analysis and must not be marketed as three-view inference. The limitation is preserved because multi-image provider work was outside the approved narrow change.
